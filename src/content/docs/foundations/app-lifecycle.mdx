A user is halfway through an insurance claim in your app. Step 3 asks for the policy number, so they switch to their email app, find it, copy it and switch back. Your app shows its splash screen, then step 1, with every field empty.

Nothing crashed. There is no stack trace and no error in your logs. While the user was reading email, the OS needed memory, killed your process and kept only a screenshot in the app switcher. Tapping that screenshot started a new process, and your code had no idea a claim was in progress.

## The OS owns your process

On a desktop, a program runs until the user quits it. On a phone, the OS decides. Memory is small, there is no large swap file to hide behind, and the foreground app must stay fast. So both platforms treat backgrounded apps as a cache: they stay in memory to make switching back instant, and they are evicted when something else needs the space.

- **Android** ranks processes by importance: foreground, visible, service, cached. A cached process holds an app the user has left, and the low memory killer removes cached processes first ([Processes and app lifecycle](https://developer.android.com/guide/components/activities/process-lifecycle)). Android 17 also enforces per-app memory limits based on the device's RAM ([behavior changes](https://developer.android.com/about/versions/17/behavior-changes-all)).
- **iOS** moves a backgrounded app to the suspended state shortly after it leaves the screen. A suspended app is in memory but runs no code. When memory runs low, the system (the mechanism is called jetsam) terminates suspended apps, and it can terminate a foreground app that exceeds its memory limit ([jetsam event reports](https://developer.apple.com/documentation/xcode/identifying-high-memory-use-with-jetsam-event-reports)).

Neither platform runs your code at the moment of the kill. A suspended or cached process is not executing, so there is no callback to save anything. The last code you can count on runs when the app leaves the foreground.

## The same states under different names

| State | Android `Activity` | iOS scene | React Native `AppState` | Flutter `AppLifecycleState` |
| --- | --- | --- | --- | --- |
| On screen, receiving input | Resumed | Foreground active | `active` | `resumed` |
| On screen, no input | Paused (after `onPause`) | Foreground inactive | `inactive` on iOS, `background` on Android | `inactive` |
| Off screen | Stopped (after `onStop`) | Background, then suspended | `background` | `hidden`, then `paused` |
| Process killed | No callback | No callback | No callback | No callback |

Compose Multiplatform exposes the Android names on every platform through a common `Lifecycle`. On iOS it maps `willResignActive` to `ON_PAUSE`, `didEnterBackground` to `ON_STOP`, `willEnterForeground` to `ON_START` and `didBecomeActive` to `ON_RESUME` ([CMP lifecycle docs](https://kotlinlang.org/docs/multiplatform/compose-lifecycle.html)).

## Sort state by how long it must live

The stack-neutral pattern starts with a question about each piece of state on a screen: if the process died right now, what should the user find when they come back?

| Kind of state | Examples | Keep it in | After a kill |
| --- | --- | --- | --- |
| App data | Cart contents, sent messages, settings | Disk or server, written when it changes | Still there |
| UI state worth restoring | Navigation stack, selected tab, scroll position, draft text | The platform's saved-state mechanism, or disk | Restored if you saved it |
| Rebuildable state | Loaded lists, decoded images, animation progress | Memory only | Gone, loaded again |

The rest of the pattern follows from the table:

1. **Write app data when it changes.** There is no reliable "app is exiting" moment to flush it.
2. **Save small keys for UI state as the app leaves the foreground.** Save the product ID, not the product. Saved-state storage is small and serialized on the main thread.
3. **Treat launch as possibly a restore.** A new process checks for saved UI state before showing the default first screen, then reloads data using the saved keys.
4. **Respect a deliberate close.** When the user swipes the app away, both platforms discard saved UI state, and the next launch starts fresh.

## Reacting to lifecycle changes

A video screen should pause playback when the app is no longer in front, and resume when it returns.

<Tabs syncKey="stack">
<TabItem label="Android">
```kotlin
@Composable
fun PlayerScreen(player: Player) {
    LifecycleStartEffect(player) {
        player.play()                       // on ON_START
        onStopOrDispose { player.pause() }  // on ON_STOP or disposal
    }
}
```
`LifecycleStartEffect` (Lifecycle 2.7+) pairs the started and stopped events. Under it sit the `Activity` callbacks: `onCreate`, `onStart`, `onResume`, `onPause`, `onStop`, `onDestroy` ([Activity lifecycle](https://developer.android.com/guide/components/activities/activity-lifecycle)). `onDestroy` does not run when the process is killed. For whole-app foreground and background events, observe `ProcessLifecycleOwner`.
</TabItem>
<TabItem label="iOS">
```swift
struct PlayerScreen: View {
    @Environment(\.scenePhase) private var scenePhase
    let player: Player

    var body: some View {
        VideoView(player: player)
            .onChange(of: scenePhase) { _, phase in
                if phase == .active { player.play() } else { player.pause() }
            }
    }
}
```
`scenePhase` is `.active`, `.inactive` or `.background` ([ScenePhase](https://developer.apple.com/documentation/swiftui/scenephase)). In UIKit the same events arrive at your `UISceneDelegate` as `sceneWillResignActive` and `sceneDidEnterBackground` ([Managing your app's life cycle](https://developer.apple.com/documentation/uikit/managing-your-app-s-life-cycle)). After entering the background you get about five seconds. For work that needs longer, such as finishing an upload, wrap it in `beginBackgroundTask` ([Apple docs](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time)).
</TabItem>
<TabItem label="React Native">
```tsx
function PlayerScreen({ player }: { player: Player }) {
  useEffect(() => {
    const sub = AppState.addEventListener('change', (state) => {
      if (state === 'active') player.play();
      else player.pause();
    });
    return () => sub.remove();
  }, [player]);

  return <VideoView player={player} />;
}
```
`AppState` reports `active`, `background` and, on iOS only, `inactive` ([AppState docs](https://reactnative.dev/docs/appstate)). On Android it reports `background` as soon as another Activity covers yours, including system ones such as an autofill picker. The events come from the native shell, so your handler runs only while the OS still gives the process CPU time.
</TabItem>
<TabItem label="Flutter">
```dart
class _PlayerScreenState extends State<PlayerScreen> {
  late final AppLifecycleListener _listener;

  @override
  void initState() {
    super.initState();
    _listener = AppLifecycleListener(
      onResume: widget.player.play,
      onInactive: widget.player.pause,
    );
  }

  @override
  void dispose() {
    _listener.dispose();
    super.dispose();
  }

  @override
  Widget build(BuildContext context) => VideoView(player: widget.player);
}
```
`AppLifecycleListener` (Flutter 3.13+) has a callback per transition: `onInactive`, `onHide`, `onPause`, `onRestart`, `onShow`, `onResume` ([API docs](https://api.flutter.dev/flutter/widgets/AppLifecycleListener-class.html)). Flutter's names do not match Android's: `Activity.onPause` produces `inactive`, and `Activity.onStop` produces `paused` ([AppLifecycleState](https://api.flutter.dev/flutter/dart-ui/AppLifecycleState.html)).
</TabItem>
<TabItem label="KMP / CMP">
```kotlin
// commonMain: the Android code, unchanged.
@Composable
fun PlayerScreen(player: Player) {
    LifecycleStartEffect(player) {
        player.play()
        onStopOrDispose { player.pause() }
    }
}
```
`lifecycle-runtime-compose` has been multiplatform since Lifecycle 2.8, so the effect APIs compile in common code. On iOS the events are driven by the UIKit notifications listed in the table above. With KMP and native UI, shared code has no lifecycle of its own: SwiftUI observes `scenePhase` and calls into Kotlin.
</TabItem>
</Tabs>

## Saving a draft in each stack

A comment box whose text should survive a process kill.

<Tabs syncKey="stack">
<TabItem label="Android">
```kotlin
@Composable
fun CommentBox() {
    var draft by rememberSaveable { mutableStateOf("") }
    TextField(value = draft, onValueChange = { draft = it })
}

// When logic needs the value, hold it in the ViewModel instead.
class CommentViewModel(private val handle: SavedStateHandle) : ViewModel() {
    val draft = handle.getStateFlow("draft", "")
    fun onDraftChange(text: String) { handle["draft"] = text }
}
```
Each holder lives a different length of time. `remember` is lost on rotation. A `ViewModel` survives rotation and dies with the process. `rememberSaveable` and `SavedStateHandle` write into the Activity's saved instance state, which the system keeps after it kills the process and hands back when the user returns ([Save UI states](https://developer.android.com/topic/libraries/architecture/saving-states)). For `@Serializable` classes there is `rememberSerializable`, and `SavedStateHandle.saved { }` since Lifecycle 2.9. Jetpack Navigation saves its back stack the same way.
</TabItem>
<TabItem label="iOS">
```swift
struct CommentBox: View {
    @SceneStorage("comment.draft") private var draft = ""

    var body: some View {
        TextField("Add a comment", text: $draft)
    }
}
```
`@State` lives as long as the process. `@SceneStorage` has the same shape, and the system saves and restores it per scene ([SceneStorage](https://developer.apple.com/documentation/swiftui/scenestorage)). Keep the values lightweight. For navigation, `NavigationPath` offers a `codable` representation you can store and reload ([NavigationPath](https://developer.apple.com/documentation/swiftui/navigationpath)). UIKit apps return an `NSUserActivity` from `stateRestorationActivity(for:)` in the scene delegate ([Restoring your app's state](https://developer.apple.com/documentation/uikit/restoring-your-app-s-state)).
</TabItem>
<TabItem label="React Native">
```tsx
import { useMMKVString } from 'react-native-mmkv';

function CommentBox() {
  const [draft, setDraft] = useMMKVString('comment.draft');
  return <TextInput value={draft ?? ''} onChangeText={setDraft} />;
}
```
React Native does not expose the platform's saved-state mechanism to JavaScript. When the process dies the JavaScript heap goes with it, and the next launch renders the root component from scratch. Restoring means persisting to disk yourself. [MMKV](https://github.com/mrousavy/react-native-mmkv) (V4 shown here) reads synchronously, so the first render already has the draft. Navigation state is persisted the same way: React Navigation 7 takes `initialState` and `onStateChange` props ([state persistence](https://reactnavigation.org/docs/state-persistence/)), and React Navigation 8, in pre-release as of its July 2026 progress report, replaces them with a `persistor` prop ([upgrade guide](https://reactnavigation.org/docs/8.x/upgrading-from-7.x/)).
</TabItem>
<TabItem label="Flutter">
```dart
// Turn restoration on for the app.
MaterialApp(
  restorationScopeId: 'app',
  home: const CommentScreen(),
);

// Built-in widgets restore themselves when given an ID.
const TextField(restorationId: 'comment_draft');

// Custom state: Restorable properties registered through RestorationMixin.
class _CounterState extends State<Counter> with RestorationMixin {
  final _count = RestorableInt(0);

  @override
  String? get restorationId => 'counter';

  @override
  void restoreState(RestorationBucket? oldBucket, bool initialRestore) {
    registerForRestoration(_count, 'count');
  }
  // build() reads _count.value
}
```
Restoration is off until you set `restorationScopeId`. The framework sends restoration data to the engine as state changes, because the OS gives no time to collect it at kill time. On Android the data travels in the saved instance state ([Restore state on Android](https://docs.flutter.dev/platform-integration/android/restore-state-android)). iOS needs extra setup in Xcode ([Restore state on iOS](https://docs.flutter.dev/platform-integration/ios/restore-state-ios)).
</TabItem>
<TabItem label="KMP / CMP">
```kotlin
// commonMain: same API as Android.
@Composable
fun CommentBox() {
    var draft by rememberSaveable { mutableStateOf("") }
    TextField(value = draft, onValueChange = { draft = it })
}
```
`SavedStateHandle` is multiplatform since Lifecycle 2.9, and `ViewModel` works in common code as long as you pass a factory, because non-JVM targets cannot create one by reflection ([CMP ViewModel docs](https://kotlinlang.org/docs/multiplatform/compose-viewmodel.html)). On Android these values ride in the Activity's saved state as usual. For iOS, the CMP lifecycle docs describe event mapping only, with no hookup to UIKit state restoration, so write drafts to disk there. DataStore Preferences supports KMP ([docs](https://developer.android.com/kotlin/multiplatform/datastore)). With KMP and native UI, the SwiftUI side uses `@SceneStorage` as in the iOS tab.
</TabItem>
</Tabs>

Answer to the Brain Power question: only native Android brings back the detail screen without extra code, because Jetpack Navigation saves its back stack. The comment returns too if the field uses `rememberSaveable`. SwiftUI, React Native and Flutter all show the home screen until you opt in with `@SceneStorage`, persisted navigation state or `restorationScopeId`.

<Aside type="caution" title="Watch it!">
Saved state is for keys and short strings. Android's saved instance state travels through Binder, whose transaction buffer is 1 MB shared across the whole process. Exceed it and the app crashes with `TransactionTooLargeException`. Google recommends staying under 50 KB ([Parcelables and bundles](https://developer.android.com/guide/components/activities/parcelables-and-bundles)). Flutter's restoration data on Android has the same ceiling. Apple also warns against putting sensitive data in `SceneStorage`.
</Aside>

## Configuration changes

Android has a second kind of teardown that the other platforms lack. When the configuration changes (rotation, window resize, dark mode, locale, font scale), the system destroys the `Activity` and creates a new one with the new resources. The process stays alive. `ViewModel` exists to carry state across that gap, and it is why the "Memory" row in the diagram above has an asterisk ([Handle configuration changes](https://developer.android.com/guide/topics/resources/runtime-changes)).

Recent Android releases changed when it happens:

- Apps that target Android 16 (API 36) have their orientation and resizability restrictions ignored on displays 600dp and wider, with a temporary opt-out. Targeting Android 17 (API 37) removes the opt-out ([Android 17 changes](https://developer.android.com/about/versions/17/changes/ff-restrictions-ignored)). A phone-only app locked to portrait will be rotated and resized on tablets and foldables.
- Android 17 stops recreating activities for keyboard, navigation, touchscreen and colour mode changes. The activity receives `onConfigurationChanged` instead ([runtime changes](https://developer.android.com/guide/topics/resources/runtime-changes)).

React Native and Flutter sidestep recreation. Their template manifests declare `android:configChanges` for orientation, screen size, UI mode and more, so the single host `Activity` stays alive and the framework re-lays out for the new size. JavaScript and Dart state survive rotation with no work from you.

iOS has no equivalent. Rotation and size changes update the trait environment, and your views and their state stay alive.

<Aside type="caution" title="Watch it!">
A React Native app still meets Activity recreation. After a process kill, Android rebuilds the host `Activity` from its saved instance state and tries to restore the fragments that `react-native-screens` created. The app then crashes with "Screen fragments should never be restored". The library's README has the fix: set `RNScreensFragmentFactory` on the fragment manager in `MainActivity.onCreate` ([react-native-screens](https://github.com/software-mansion/react-native-screens#android)).
</Aside>

## Trade-offs and scale

**Restore keys, then reload.** A restored screen gets its ID from saved state and its content from the database or network. That keeps saved state small, and it means a restore shows current data instead of a stale copy.

**Saved state outlives the code that wrote it.** State you persist to disk can be read by the next app version after an update. React Navigation's docs put a version in the storage key (`NAVIGATION_STATE_V1`) for this reason. Treat any restored blob as untrusted input: if it fails to parse, fall back to the default screen.

**Deep links compete with restoration.** If the app is launched by a link, the link should win. React Navigation's persistence example checks `Linking.getInitialURL()` and skips restoring when a URL is present.

**Some screens should not come back.** A payment confirmation or a one-time code screen restored a day later does more harm than starting over. Decide per flow, and expire saved drafts.

**Test the kill.** Rotating the device or enabling "Don't keep activities" tests Activity recreation, which is not the same thing: the process and every singleton in it stay alive. To test a real kill on Android, press Home, then run `adb shell am kill <package>`, which only kills processes that are safe to kill, the same condition the system applies ([adb docs](https://developer.android.com/tools/adb)). On iOS, send the app to the background and stop it from Xcode. Swiping it away in the app switcher tests the wrong path, because that discards saved state. In automated tests, Compose has `StateRestorationTester` and Flutter has `WidgetTester.restartAndRestore()`.

**Measure it in production.** On Android 11+, `ActivityManager.getHistoricalProcessExitReasons()` returns an `ApplicationExitInfo` for recent process deaths, including `REASON_LOW_MEMORY` ([API reference](https://developer.android.com/reference/android/app/ApplicationExitInfo)). On iOS, MetricKit's `MXAppExitMetric` counts foreground and background exits by cause, including memory limit terminations ([MXBackgroundExitData](https://developer.apple.com/documentation/metrickit/mxbackgroundexitdata)). A rising background kill rate usually means the app holds too much memory when it leaves the foreground.

**Make it part of the screen contract.** In a large app, restoration breaks one screen at a time as teams add state. Require navigation arguments to be small and serializable, and run a restore test for each new screen in CI.

<NoDumbQuestions>
<dt>Couldn't the OS call my code right before it kills the process?</dt>
<dd>The process is suspended to save memory and battery. Waking every cached app to let it run cleanup code would use the resources the system is trying to free, at the moment it has the least to spare.</dd>

<dt>Is swiping the app away the same as process death?</dt>
<dd>No. The system treats it as the user saying "I'm done". Saved UI state is thrown away and the next launch is a fresh start. Data on disk stays.</dd>

<dt>Does a `ViewModel` survive process death?</dt>
<dd>No. It survives configuration changes because it lives in memory outside the Activity. To survive a kill, the values must go through `SavedStateHandle` or to disk.</dd>

<dt>If I write every keystroke to disk, do I still need saved state?</dt>
<dd>Disk works, and it is the only option in React Native. The difference is cleanup: the OS scopes saved state to the task or scene and discards it when the user closes the app, while anything on disk stays until your code deletes it.</dd>

<dt>Can iOS kill my app while it is on screen?</dt>
<dd>Yes, if it exceeds its memory limit. The user sees the app vanish, and you get a jetsam event report instead of a crash report.</dd>
</NoDumbQuestions>

## Sidebar: other stacks

- **.NET MAUI** raises cross-platform lifecycle events on its `Window` class (`Created`, `Activated`, `Deactivated`, `Stopped`, `Resumed`, `Destroying`) and maps them to the platform callbacks.
- **Ionic / Capacitor** apps listen to the `App` plugin's `appStateChange` event. The web view's JavaScript state is lost with the process, as in React Native, so drafts go to storage.
