You join a team that ships a Flutter app. A crash report lands in your inbox, and the stack trace has Java frames, C++ frames and Dart frames in it. Which of them is the bug in? You can only answer that if you know which pieces of software are running inside the app and how they talk to each other.

This chapter gives you that picture for every stack in this book. Every later chapter leans on it: state management, navigation, background work and performance all behave the way they do because of the runtime underneath.

## Every app is a native app first

The operating system only knows how to launch one kind of thing: a native app. Android starts an APK's process and creates its `Application` and launcher `Activity`. iOS loads a Mach-O binary and calls its `main` function. Neither OS has heard of React Native, Flutter or Compose Multiplatform.

So every cross-platform app is a real Android app and a real iOS app with a small native shell. The shell's job is to boot a runtime and hand it a surface to draw on. You can see the shell in any project:

That shell is where you, the native developer, come back in. Push tokens, deep links, permissions and app lifecycle events all arrive at the native shell first. Cross-platform frameworks forward them to your shared code, and when the forwarding has a gap, someone writes Kotlin or Swift to fill it.

### Native Android

Kotlin compiles to JVM bytecode, and the D8 compiler converts that to DEX bytecode ([docs](https://developer.android.com/tools/d8)). Android Runtime (ART) runs it with a mix of interpretation, JIT and ahead-of-time compilation guided by profiles. Baseline Profiles let you ship a list of hot code paths so ART can compile them at install time, which is why they help startup ([docs](https://developer.android.com/topic/performance/baselineprofiles/overview)).

Every app process is forked from **Zygote**, a process that starts at boot with the framework classes and resources already loaded. The fork shares those memory pages copy-on-write, so a new app does not pay to load the framework again ([Android docs: memory overview](https://developer.android.com/topic/performance/memory-overview)).

Your UI code runs on the **main thread**, a `Looper` that processes one message at a time: input events, lifecycle callbacks, frame callbacks from `Choreographer`. Block it for five seconds during input handling and you get an ANR ([docs](https://developer.android.com/topic/performance/vitals/anr)).

### Native iOS

Swift compiles straight to ARM machine code. There is no VM and no garbage collector. Memory is managed with Automatic Reference Counting (ARC), where the compiler inserts retain and release calls. Reference cycles leak, which is why you see `[weak self]` all over iOS code.

At launch the system loads your binary and its frameworks, then `UIApplicationMain` creates the application object and starts the **main run loop** ([Apple: About the app launch sequence](https://developer.apple.com/documentation/uikit/about-the-app-launch-sequence)). With SwiftUI's `@main App` you never see this call, but it still happens. UIKit apps built with the iOS 27 SDK must use the scene-based lifecycle (`UISceneDelegate`) or they will not launch ([iOS 27 release notes](https://developer.apple.com/documentation/ios-ipados-release-notes/ios-ipados-27-release-notes), [TN3187](https://developer.apple.com/documentation/technotes/tn3187-migrating-to-the-uikit-scene-based-life-cycle)). The rule covers the native shells of cross-platform apps too: Flutter migrates eligible apps automatically since 3.41 ([Flutter docs](https://docs.flutter.dev/release/breaking-changes/uiscenedelegate)), and React Native added `SceneDelegate` support in 0.88 ([release post](https://reactnative.dev/blog/2026/10/19/react-native-0.88)).

The main thread is the only thread allowed to touch UI. Swift Concurrency encodes that rule in the type system as `@MainActor` ([docs](https://developer.apple.com/documentation/swift/mainactor)), so the compiler rejects UI updates from a background task.

### React Native

A React Native app ships a JavaScript bundle. In release builds the bundle is compiled to **Hermes bytecode** at build time, so the phone skips parsing JavaScript source on startup ([docs](https://reactnative.dev/docs/hermes)). Hermes V1 is the default engine since React Native 0.84 ([release post](https://reactnative.dev/blog/2026/02/11/react-native-0.84)).

Since 0.82 the **New Architecture** is the only architecture ([release post](https://reactnative.dev/blog/2025/10/08/react-native-0.82)). You will still find blog posts about "the bridge", an asynchronous queue of JSON messages between JavaScript and native. That design is gone. Its replacements:

- **JSI** (JavaScript Interface): a C++ API that lets JavaScript hold references to C++ objects and call them directly ([docs](https://reactnative.dev/architecture/landing-page)), including synchronously ([0.76 release post](https://reactnative.dev/blog/2024/10/23/the-new-architecture-is-here)).
- **Fabric**: the renderer. It turns your React tree into real platform views.
- **Turbo Native Modules**: native modules exposed through JSI, with typed interfaces generated by Codegen ([docs](https://reactnative.dev/docs/turbo-native-modules-introduction)).

Fabric works in phases ([docs: render pipeline](https://reactnative.dev/architecture/render-pipeline)). In **render**, React runs your components on the JavaScript thread and the renderer builds a C++ "shadow tree". In **commit**, Yoga computes layout (Flexbox) for that tree. In **mount**, the UI thread creates or updates real `android.view.View` and `UIView` objects to match.

### Flutter

Dart code is compiled to machine code ahead of time (AOT) for release builds. Debug builds run on the Dart VM with a JIT compiler, which is what makes stateful hot reload possible.

The native shell (`FlutterActivity`, `FlutterViewController`) is the **embedder**. It starts the Flutter engine, a C++ library, and gives it a surface to draw into ([Flutter architectural overview](https://docs.flutter.dev/resources/architectural-overview)). From then on Flutter owns every pixel on that surface. A Flutter button is not an `android.widget.Button` or a `UIButton`. It is shapes and text that Flutter paints.

Painting goes through **Impeller**, Flutter's renderer, which precompiles its shaders at build time so animations do not stutter on first run. Impeller is the only renderer on iOS. On Android it is the default on API 29+, and devices on older Android versions or without Vulkan fall back to the legacy OpenGL renderer ([docs: Impeller](https://docs.flutter.dev/perf/impeller)).

Flutter used to run Dart on its own UI thread, separate from the platform's main thread. Since Flutter 3.29, Dart runs **on the platform main thread** on iOS and Android ([architectural overview](https://docs.flutter.dev/resources/architectural-overview)). That makes synchronous calls into native APIs possible, and it means a slow Dart function now blocks the same thread Android watches for ANRs. Heavy work belongs in an **isolate**, Dart's unit of concurrency with its own memory heap.

### Kotlin Multiplatform and Compose Multiplatform

Kotlin Multiplatform (KMP) is not a runtime. It is a compiler setup that builds the same Kotlin source for several targets:

- On Android, Kotlin takes the same path as any Android code: JVM bytecode, then DEX, run by ART. There is no extra runtime.
- On iOS, **Kotlin/Native** compiles Kotlin to machine code through LLVM and packages it as an Apple framework. That framework carries a small runtime with its own tracing garbage collector ([docs](https://kotlinlang.org/docs/native-memory-manager.html)), which cooperates with Swift's ARC at the boundary ([docs](https://kotlinlang.org/docs/native-arc-integration.html)).

Swift sees Kotlin through Objective-C headers today, which is why some Kotlin APIs look clumsy from Swift (sealed classes, generics, default arguments). **Swift export**, which generates Swift APIs directly, is in Beta as of Kotlin 2.5.0-RC ([Kotlin 2.5.0-RC notes](https://kotlinlang.org/docs/whatsnew-eap.html)).

{/* whatsnew-eap.html always describes the current preview release. When Kotlin 2.5.0 ships, point this link at the versioned "What's new in Kotlin 2.5.0" page and re-check the stability level. */}

KMP on its own shares logic: networking, storage, business rules. Each platform keeps its own UI. **Compose Multiplatform** (CMP) adds shared UI. On Android it is Jetpack Compose. On iOS it renders with Skia into a Metal-backed view hosted by a `UIViewController`, so it draws its own pixels the way Flutter does. CMP for iOS is stable since 1.8.0 (May 2025) ([JetBrains blog](https://blog.jetbrains.com/kotlin/2025/05/compose-multiplatform-1-8-0-released-compose-multiplatform-for-ios-is-stable-and-production-ready/)), and rendering runs on a separate render thread by default since 1.11.

<Aside type="note" title="If you only know Android">
KMP is the stack where your existing knowledge transfers most directly. Coroutines, Flow, Ktor, Room (which supports KMP) and Compose all work in shared code. The new parts are Kotlin/Native's memory and threading rules on iOS, Xcode builds and the Swift-facing API of your module.
</Aside>

**Platform-owned components.** SwiftUI and UIKit draw Apple's controls. React Native's `<Text>` becomes a real text view on each platform, and libraries like `react-native-screens` use the platform's own navigation containers. When Apple restyles its controls, as it did with Liquid Glass in iOS 26, native apps pick up much of the new look when rebuilt with the new SDK. React Native apps get it wherever they use platform containers and controls.

**Framework-owned components, platform graphics.** Jetpack Compose does not create a `TextView` for each `Text`. A single `AndroidComposeView` hosts the whole composition, and Compose draws text and shapes itself through Android's hardware-accelerated graphics pipeline. It still uses the platform's text rendering, accessibility services and input system.

**Framework-owned components and renderer.** Flutter and CMP on iOS paint everything with their own engine. You get identical pixels on every device and full control over every frame. In exchange, the framework has to reimplement platform behaviour: text selection handles, scroll physics, accessibility trees, keyboard handling and new design languages. Flutter's Cupertino widgets do not change when iOS changes. CMP 1.11 added an opt-in native `UIView`-based text input on iOS for exactly this reason ([CMP 1.11 notes](https://kotlinlang.org/docs/multiplatform/whats-new-compose-111.html)).

Answer to the Brain Power question: only **React Native** produces an Android `View` holding the text. Compose draws the text inside one host view, and Flutter paints it onto its surface.

| Consequence | Platform-owned (UIKit, SwiftUI, Android Views, RN) | Compose on Android | Self-rendered (Flutter, CMP iOS) |
| --- | --- | --- | --- |
| Looks native by default | Yes | Yes, through the Material 3 library ([docs](https://developer.android.com/develop/ui/compose/designsystems/material3)) | Only as far as the widget set imitates it |
| Gets new OS design automatically | Mostly | No, Material components ship in a library you update | No, waits for framework updates |
| Same pixels on both platforms | No | Android only | Yes |
| Embedding a native map or WebView | Trivial | Through the `AndroidView` composable ([docs](https://developer.android.com/develop/ui/compose/migrate/interoperability-apis/views-in-compose)) | Possible through platform views, with a performance cost |
| Accessibility | Comes from the platform | Semantics tree that Android's accessibility services read ([docs](https://developer.android.com/develop/ui/compose/accessibility/semantics)) | Framework builds a semantics tree and translates it |

- **React Native**: native code is exposed as Turbo Native Modules (logic) or Fabric native components (views). You declare a typed spec in TypeScript and Codegen produces the C++ and native glue. Expo Modules offer a Swift and Kotlin API on top of the same machinery.
- **Flutter**: the long-standing route is **platform channels**, which serialize messages between Dart and native code asynchronously. **Pigeon** generates type-safe channel code. Since Flutter 3.50, direct native interop through FFI and JNI with generated bindings (FFIgen for C and Objective-C, JNIgen for Java and Kotlin) is stable ([Flutter 3.50 announcement](https://flutter.dev/blog/whats-new-in-flutter-3-50)).
- **KMP**: there is no bridge to cross. `expect` declarations in common code get `actual` implementations per platform, and those implementations call platform APIs directly. iOS code in Kotlin can import `platform.UIKit` and `platform.Foundation`, because Kotlin/Native generates bindings for Apple's Objective-C frameworks.

## Consequences for the rest of the book

Knowing the runtime lets you predict behaviour that later chapters cover in detail.

**Startup.** A native app starts its process and draws. A cross-platform app also has to load its runtime: the Hermes VM and bundle, or the Flutter engine and Dart snapshot. This shows up in cold start traces and is why "time to first frame" is a standard metric for these stacks.

**App size.** Every engine ships inside your app. Flutter carries its engine and Impeller, React Native carries Hermes and its C++ core, and CMP on iOS carries Skia and the Kotlin/Native runtime.

**Crashes and debugging.** Release builds strip names. A React Native crash needs JavaScript source maps ([docs](https://reactnative.dev/docs/debugging-release-builds)), Flutter needs the Dart symbol files from `--split-debug-info` ([docs](https://docs.flutter.dev/deployment/obfuscate)), and Kotlin/Native needs the dSYM generated for its framework ([docs](https://kotlinlang.org/docs/native-debugging.html)). Stack traces mix languages, as in the opening example.

**Shipping fixes.** A JavaScript bundle is data the app loads, so React Native apps can replace it over the air (Expo Updates is the common tool) within the app store rules. Native code always needs a store release. The release chapter covers the details.

**Threading bugs.** Each stack has a "never block this thread" rule, but the thread differs. React Native has the JavaScript thread and the UI thread. Flutter's Dart code can block the platform main thread, so heavy work goes to isolates, and slow GPU work on the raster thread drops frames too ([DevTools docs](https://docs.flutter.dev/tools/devtools/performance)).

<NoDumbQuestions>
<dt>Is React Native "native" then?</dt>
<dd>Its UI is: the views on screen are platform views. Its logic is not: your code runs as JavaScript in Hermes. That is why it feels native for standard screens and why heavy JavaScript work can still cause jank.</dd>

<dt>Is Compose Multiplatform on iOS just Flutter written in Kotlin?</dt>
<dd>On iOS the rendering approach is similar, since both draw with their own engine. The difference is everything around the UI: CMP compiles to native code that calls Apple frameworks directly, with no message channel, and it shares its UI API with Jetpack Compose on Android.</dd>

<dt>Does KMP replace Swift on iOS?</dt>
<dd>No. A typical KMP app shares data and domain layers and keeps SwiftUI on iOS. With CMP you can share UI too, but the app entry point, Xcode project and platform integrations remain Swift.</dd>

<dt>Can I still find the old React Native "bridge" in my app?</dt>
<dd>You can't run on it: since 0.82 the Legacy Architecture can no longer be enabled ([release post](https://reactnative.dev/blog/2025/10/08/react-native-0.82)). Its code is still being deleted release by release, and 0.84 removed more `com.facebook.react.bridge` classes ([release post](https://reactnative.dev/blog/2026/02/11/react-native-0.84)). Older libraries written for the bridge run through an interop layer.</dd>
</NoDumbQuestions>

| Entry point | `Application`, `Activity` | `@main App` or `UIApplicationDelegate` + `UISceneDelegate` | `ReactActivity` / `AppDelegate` booting `AppRegistry` | `FlutterActivity` / `FlutterViewController` calling `main()` | Native shells, shared `App()` composable |
| Language | Kotlin | Swift | TypeScript | Dart | Kotlin |
| Runs on | ART | Native code | Hermes VM | Native code + Flutter engine | ART (Android), native code (iOS) |

## Sidebar: other stacks you will meet

- **.NET MAUI**: C# on the .NET runtime. UI controls are mapped to platform controls through "handlers", so it sits with React Native in the platform-owned group.
- **Ionic / Capacitor**: a web app running in the platform WebView, with a plugin bridge to native APIs. The rendering is the browser engine's.
- **Lynx** (ByteDance): JavaScript UI framework that renders native views, with a dual-thread design that keeps the main thread free of app logic.
