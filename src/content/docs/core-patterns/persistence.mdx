A notes app stores everything on a server and fetches it on launch. The bug reports:

- A user writes a note in the underground. The save fails, they close the app, and the note is gone.
- Version 2.3 adds a "pinned" column. Users who update from 2.1 crash on launch, and reinstalling loses their data.
- A security review finds the session token in a plain preferences file.
- A user edits the same note on a phone and a tablet. One edit disappears without a trace.

The first bug is an app that needs the network to accept a write. The second is a schema change without a migration. The third is the wrong store for the data. The fourth is a missing conflict rule.

<BrainPower>
A user is offline and taps "delete" on a note. The app removes the row from its local database immediately. When the connection returns, how does the app know it still owes the server a delete?
</BrainPower>

## Constraints on a phone

- **Storage is private and small.** Each app has a sandboxed directory. The OS can clear the cache directory when space runs low, and the user can clear everything.
- **The process can die during a write.** A half-written file is corrupt. Databases solve this with transactions, and plain files need atomic replace ([app lifecycle](/foundations/app-lifecycle/)).
- **The schema lives on the user's device.** Every version of your database format that ever shipped still exists on some phone. An update has to migrate each of them forward, in one step or many.
- **Backups copy the data elsewhere.** Android Auto Backup and iCloud backup restore app files onto a new device, including files you assumed were tied to the old one ([Auto Backup](https://developer.android.com/identity/data/autobackup)).
- **Connectivity is not guaranteed.** Reads and writes that need the server will fail on a regular basis ([networking](/core-patterns/networking/)).

## The pattern: the database is the source of truth

In an offline-first app the UI never waits for the network. It reads from the local database and writes to the local database. A separate sync process moves changes between the database and the server.

```d2
classes: {
  box: { style: { font-size: 16 } }
  ui: { style: { fill: "#D6E8FF"; font-color: "#1F1F1F"; font-size: 16 } }
  db: { style: { fill: "#D9F5DD"; font-color: "#1F1F1F"; font-size: 16 } }
  sync: { style: { fill: "#FFF4C2"; font-color: "#1F1F1F"; font-size: 16 } }
}
direction: down
ui: "UI\nobserves a query" { class: ui }
repo: "Repository" { class: box }
db: "Local database\nnotes + outbox" { class: db; shape: cylinder }
sync: "Sync\nruns when online" { class: sync }
server: "Server" { class: box }
ui -> repo: "write" { style.font-size: 16 }
repo -> db: "1. save + queue" { style.font-size: 16 }
db -> ui: "2. query emits" { style.font-size: 16 }
db -> sync: "3. pending\nchanges" { style.font-size: 16 }
sync -> server: "4. push" { style.font-size: 16 }
server -> sync: "5. pull" { style.font-size: 16 }
sync -> db: "6. apply" { style.font-size: 16 }
```

1. **Reads are observable queries.** The UI subscribes to "all notes, newest first". When any code changes the table, the query emits a new list and the screen redraws ([state management](/core-patterns/state-management/)).
2. **Writes go to the database first.** The note is saved locally and appears on screen within a frame.
3. **Pending changes are recorded in an outbox.** In the same transaction as the write, the app adds a row describing what the server still needs to hear: "create note 17", "delete note 9". This answers the Brain Power question. The outbox row survives app restarts, and the delete is sent when the connection returns.
4. **Sync drains the outbox and pulls changes.** It runs when the app is open and online, and from a background job otherwise ([background work](/core-patterns/background-work/)). Each outbox entry carries an ID so the server can ignore a repeat ([idempotency](/core-patterns/networking/#retries-and-idempotency)).
5. **Conflicts have a written rule.** When the server and the device both changed a record, one documented rule decides the result.
6. **Schema changes ship with migrations.** Every schema version has a tested path to the next.

Android's guide describes this design under the name offline-first ([build an offline-first app](https://developer.android.com/topic/architecture/data-layer/offline-first)), and Flutter's guide has the same pattern ([offline-first support](https://docs.flutter.dev/app-architecture/design-patterns/offline-first)).

## An observable query in each stack

The same job in each stack: a notes table, a query the UI observes, and an insert.

    @PrimaryKey val id: String,
    val body: String,
    val updatedAt: Long,
    val pinned: Boolean = false,

@Dao

Room generates the implementation from annotated interfaces and checks the SQL against the schema at compile time ([save data with Room](https://developer.android.com/training/data-storage/room)). A query that returns a `Flow` re-runs whenever its tables change. Room 3.0 (`androidx.room3`, stable since July 2026) is a Kotlin-first rewrite: coroutine-only, KSP-only and built on a multiplatform SQLite driver in place of Android's `SupportSQLite` API ([Room 3.0 release notes](https://developer.android.com/jetpack/androidx/releases/room3)). Most existing apps are on Room 2.x in the `androidx.room` package. Settings go in DataStore (1.2), which replaces `SharedPreferences` with an asynchronous, transactional API ([DataStore](https://developer.android.com/topic/libraries/architecture/datastore)).

## Migrations

The launch crash from the opening happened because version 2.3 expected a `pinned` column and the file on disk came from 2.1. A migration is code that changes an existing database file from schema version N to N+1. On update, the library runs every step between the version on disk and the current one.

| Stack | Schema version | Migration mechanism |
| --- | --- | --- |
| Room | `version` in `@Database` | `@AutoMigration` for additive changes, `Migration` objects for the rest, exported schema JSON for tests ([migrate your Room database](https://developer.android.com/training/data-storage/room/migrating-db-versions)) |
| SwiftData | `VersionedSchema` | Automatic lightweight migration, or stages in a `SchemaMigrationPlan` ([SchemaMigrationPlan](https://developer.apple.com/documentation/swiftdata/schemamigrationplan)) |
| expo-sqlite + Drizzle | Migration files | `drizzle-kit` generates SQL files, applied at startup with `useMigrations` |
| drift | `schemaVersion` | `MigrationStrategy.onUpgrade`, with generated step-by-step helpers ([drift migrations](https://drift.simonbinder.eu/migrations/)) |
| SQLDelight | Numbered `.sqm` files | Each file holds the SQL from one version to the next ([SQLDelight migrations](https://sqldelight.github.io/sqldelight/latest/android_sqlite/migrations/)) |

Rules that hold for all of them:

- Commit the schema of every released version to the repository. The migration test opens a database at each old version, runs the migrations and checks the result.
- Test the long jump. Users skip releases, so 2.1 to 2.6 runs five migrations in a row.
- Prefer additive changes: a new nullable column or a new table. Renames and type changes need data copied by hand.
- Never edit a migration that has shipped. Write a new one.

<Aside type="caution" title="Watch it!">
Room's `fallbackToDestructiveMigration` deletes the user's data whenever a migration path is missing. It suits a pure cache that can be refetched. In an offline-first app the database holds unsynced edits, and wiping it loses work the server has never seen ([migrating Room databases](https://developer.android.com/training/data-storage/room/migrating-db-versions)).
</Aside>

## Sync and conflicts

Sync has two directions. Push sends the outbox to the server in order. Pull asks the server for everything that changed since the last sync, using a cursor or timestamp the server issued, and applies it to the local database in a transaction.

A conflict happens when the device and the server changed the same record between two syncs. The lost edit from the opening was an unhandled conflict: the second write overwrote the first.

Last write wins is the simplest rule and loses data when two people or two devices edit the same record. It also depends on clocks, and a phone's clock can be wrong, so compare versions issued by the server where you can. Collaborative editing of the same text needs a data type built for merging (a CRDT), which is a project of its own.

Sync engines take over this work. Cloud Firestore keeps a local cache and queues writes while offline ([Firestore offline data](https://firebase.google.com/docs/firestore/manage-data/enable-offline)). SwiftData and Core Data can mirror a store to CloudKit for a user's own devices ([syncing model data across devices](https://developer.apple.com/documentation/swiftdata/syncing-model-data-across-a-persons-devices)). They save months of work, and they tie your data model to the service.

## Trade-offs and scale

**Not every feature needs offline writes.** Reading cached data offline is cheap: store what you fetched. Writing offline brings the outbox, conflicts and partial failures. Decide per feature. A notes app needs offline writes. A payment should require a connection and say so.

**Show sync state.** The user needs to know whether a note has reached the server. Keep a `syncState` column (`pending`, `synced`, `failed`) and show it. Surface an edit the server rejected, and never drop it silently.

**Deletes need a marker.** If the device deletes the row at once, sync has nothing left to send, and a later pull may bring the row back. Mark the row as deleted (a tombstone), hide it from queries and remove it after the server confirms.

**Sign-out and multiple accounts.** Data from one account must not appear in the next. Use one database file per account, or delete everything on sign-out, including the outbox, the key-value store and cached files.

**Backups restore more than you expect.** A restored device can receive an old database and an old token. Exclude files that hold tokens and device-specific IDs from backup, and make sync cope with a database older than the server remembers ([Auto Backup](https://developer.android.com/identity/data/autobackup)).

**Encryption at rest.** Both platforms encrypt app storage with keys tied to the device lock. For an additional layer (health or financial data), SQLCipher encrypts the database file, with the key held in the Keystore or Keychain.

**Large tables need paging.** A query that returns 50,000 rows blocks whichever thread runs it. Page from the database with `LIMIT` and an index, through Paging 3 on Android or the list's own lazy loading elsewhere ([concurrency](/foundations/concurrency/)).

<NoDumbQuestions>
<dt>Is offline-first the same as caching?</dt>
<dd>Caching keeps a copy of server data so reads work offline. Offline-first also accepts writes offline and syncs them later, which requires the outbox and a conflict rule.</dd>

<dt>Can I store my list as JSON in the key-value store?</dt>
<dd>For ten items that never get queried, yes. The whole value is rewritten on every change and loaded whole on every read, and you get no queries, no partial updates and no migrations. Move to a database when the list grows or needs filtering.</dd>

<dt>Why do IDs in the samples come from the client?</dt>
<dd>An offline device cannot ask the server for the next ID. The app generates a UUID, uses it locally at once and sends it with the create request. The same ID then doubles as the idempotency key.</dd>

<dt>Realm, Isar, ObjectBox, WatermelonDB: should I use one instead of SQLite?</dt>
<dd>Check who maintains it first. MongoDB shut down Atlas Device Sync, the sync service behind Realm, on September 30, 2025, and deprecated the Realm SDKs with it (<a href="https://www.mongodb.com/docs/device-sync-deprecation/">deprecation notice</a>). Apps built on it had to migrate their storage and their sync. SQLite-based libraries share a file format that every tool can open, and the official guides for every stack in this book use them.</dd>

<dt>Where do downloaded images go?</dt>
<dd>In files. Image loading libraries (Coil, Kingfisher, expo-image, cached_network_image) keep their own disk cache in the cache directory, which the OS may clear. Files the user created or explicitly downloaded go in the app's documents directory, with their paths in the database.</dd>
</NoDumbQuestions>

## Sidebar: other stacks

- **.NET MAUI** uses `sqlite-net` or EF Core over SQLite, `Preferences` for settings and `SecureStorage` for secrets.
- **Ionic / Capacitor** uses the Preferences plugin for settings and a SQLite plugin for data. Browser storage inside the WebView can be cleared by the OS, so it is not a safe place for user data.
- **Lynx** has no built-in database. Persistent storage goes through native modules provided by the host app.
