The chapters in this book explain patterns. These pages answer a more practical question: you sit down at a stack you have never used, and you need to know what to install, how to create a project, which libraries a team would expect to find in it, and what the working day looks like.

There is one page per stack, all with the same sections:

- [Android](/toolkits/android/)
- [iOS](/toolkits/ios/)
- [React Native](/toolkits/react-native/)
- [Flutter](/toolkits/flutter/)
- [KMP / CMP](/toolkits/kmp/)

Versions follow the book's baseline of November 2026 ([how to read this book](/start-here/how-to-read/)). Library choices are the ones the official documentation uses or that most production codebases contain. Each page marks which is which.

## The two loops

Every stack has the same two loops. The inner loop is what you do hundreds of times a day, and its speed decides how the stack feels. The outer loop is how a change reaches users.

```d2

  store: { style: { fill: "#D9F5DD"; font-color: "#1F1F1F"; font-size: 16 } }

  style.font-size: 18

outerloop: "Outer loop: minutes to days" {
  style.font-size: 18
  grid-columns: 4
  grid-gap: 12
  pr: "Pull request" { class: outer }

  beta: "Signed build\nto testers" { class: outer }

innerloop -> outerloop: "commit" { style.font-size: 16 }
```

Every cross-platform stack builds a native app in the end ([runtime anatomy](/foundations/runtime-anatomy/)), so React Native, Flutter and KMP developers install Android Studio and Xcode as well, even if they rarely open them.

## Practices that hold in every stack

- **Pin the toolchain.** Commit the files that fix versions: the Gradle wrapper and version catalog, `Package.resolved`, the JavaScript lockfile, `pubspec.lock`. Use the same versions in CI.
- **Format and lint in CI from the first commit.** Adding a formatter to a large codebase produces one enormous diff. Adding it on day one costs nothing.
- **Keep secrets out of the repository.** Signing keys, API keys and service account files belong in the CI secret store. An API key compiled into the app can be extracted, so anything that must stay secret belongs on your server.
- **Automate the signed build early.** The first store upload always surfaces signing, icon and metadata problems. Do it in the first week with an empty app.
- **Test on a slow device.** Simulators and flagship phones hide performance problems. Keep one old, cheap Android phone on the desk.
- **Follow the official sample.** Each stack has a reference app maintained by its vendor, linked on each page. When unsure how to structure something, copy it.

Library popularity changes faster than the patterns do. The tables here were checked in November 2026. Before adding a dependency, check its last release date and whether it supports the current version of its platform.
</Aside>
